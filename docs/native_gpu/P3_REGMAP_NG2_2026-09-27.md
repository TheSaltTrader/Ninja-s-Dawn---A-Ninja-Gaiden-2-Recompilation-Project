# P3 register map for NG2 - the XDK device object as the source of the register file (2026-09-27)

Full-native plan, phase P3 stage 1 (Fable plan b9caa8a): a front end on the GAME thread that produces the register
file the backend draws from, without the plugin's PM4 parser. Stage 1 decodes each hooked call's own packets; stage
2 replaces decoded values with reads of the XDK device object where the map proves them equal. This document is the
NG2 map and the two recording facts it needed. Recorder: `src/ng2_p2_census.cpp` (`NG2_P3MAP=<guest frame>:<max
calls>`, on top of `NG2_P2`); decoders: `tools/native_gpu/p3_flush.py` (Fable's, grammar-driven) and
`tools/native_gpu/p3_flush2.py` (NG2's, plugin-boundary-driven).

## Two recording facts (leg ng2_072, guest frame 6620, 1049 calls with the device object)

**The cursor names the last dword written.** `device+0x30` at a call's entry points at the previous call's LAST
dword, and at its exit at this call's last dword. Measured: with the range's first dword skipped, the grammar decode
of 1044 of 1048 recorded ranges ends exactly ONE dword past `[cur_in, cur_out)` (the other 4 are ranges the
neighbouring frames' packets confused). A call's bytes are therefore `[cur_in + 4, cur_out + 4)`; the recorder's
format v3 records that window, the front end decodes it. (The P2 attribution by address is unaffected: a 4-byte
shift never crosses a packet's producer.)

**The foreign first dword is the previous call's tail, not a packet.** `02000200`, `0BADF00D`, `40000047`,
`0000200E` ... at `[cur_in]`: decoding it as a packet header eats hundreds of dwords (a type-0 header's count) and
loses sync - Fable's `p3_flush.py` did in 990 of 1049 NG2 ranges (Fable's XDK leaves `FFFFFFFF` there and their
decoder skips it). With the shift, the plain PM4 grammar (type 0/1/2/3, `FFFFFFFF` and `0` as fill) reproduces the
plugin's own packet boundaries in 1045 of 1048 calls.

**Robust decode.** `p3_flush2.py` does not trust the grammar at all: the plugin recorded every packet's address and
header for the same frames (`p2_packets.bin`, `NG2_P2` on), so each packet inside a call's range is decoded from the
plugin's header with its data read from the call's bytes. 68,914 plugin packets in frames 6619-6621; every one of
the 1048 calls had packets inside its range; none lay past the recorded bytes.

## The device at DRAW time (stage 2 check, `tools/native_gpu/p3_devcheck.py`)

The write-time map says which device word a register's writes come from; what stage 2 needs is whether the device
holds the register file the GPU draws with. `p3_bridge.bin` records, for every bridge draw whose packet lies in a
recorded call range, the plugin's register file at that draw - stamped with the bridge's swap count (format v3),
because the per-frame command buffers rotate through the same memory and an address-only test caught later
frames' draws (leg ng2_073: 11,182 distinct draw addresses for a frame of ~700 direct draws, 57% agreement =
contamination). Leg ng2_074, frame 6620, 675 draws inside recorded calls, the device read at the innermost
containing call's exit:

- **358 of 522 mapped registers agree on every draw**; 130 differ on <= 5% of draws (frame-boundary shape:
  the call changed the state after its draw).
- **32 differ for real:** `0x2200 RB_DEPTHCONTROL` (5%); float constants `0x4011-0x4019` (c4-c6, 12-99%: a
  per-draw matrix written straight into the packet), `0x4322/0x4323` (c200.xy, 97%), `0x443E/0x4443/0x446B`
  (pixel c15/c16/c26); fetch words `0x4803-0x4805` (5%) and the 5th word of the texture fetch constants
  `0x481C, 0x4822, ... 0x4876` (every 6th register, 84%: computed at draw time, the write-time device word was
  coincidental).
- **Five "derived" registers ARE device words at the draw:** `0x2000 RB_SURFACE_INFO -> +0x2880` (99.6%),
  `0x2082 -> +0x28C8` (97%), `0x210D -> +0x28FC` (99.6%), `0x2208 -> +0x2954` (95%), `0x2301 -> +0x29BC`
  (99.5%); `0x2100 -> +0x28CC` and `0x2204-0x2206 -> +0x2944..+0x294C` sit at 95%. (At write time the device
  word is updated after the packet is emitted, which is why the write-time map missed them.)
- **Without a device word at the draw:** the draw packet's own `0x21F9-0x21FC` (VGT draw words), `0x2203`
  (75%), the resolve pair `0x2318/0x231B`.

So a stage-2 front end for NG2 = the device words above for ~95% of the file, plus per-draw values for: the draw
packet's own words, c4-c6 / c200 / three pixel constants, the texture fetch constants' 5th word, and the resolve
registers - each of which the draw or resolve call computes and can be read at that call.

Leg ng2_075 (a second sample, 651 draws): the same 358 always-equal registers and the same 32 per-draw ones.

## Front end (NG2_P3FE) - validation of stage 1

Three designs, in the order the legs killed them:

1. **Decode each call's bytes at the outermost exit** (Fable's first version): 76 calls decoded in 3,000 frames
   (leg ng2_073) - NG2's render thread's outermost hooked function never returns during play, so the "stack empty"
   condition never holds there. (The first leg's summary printed only on matched draws and stayed silent; the report
   now prints at every 20,000 bridge draws and at the window's end, unconditionally.)
2. **A per-thread cursor high-water mark**, decoding [hwm + 4, cur + 4) at every hook event (leg ng2_074): 72,500
   draws compared, but 12.1 M bridge draws had no snapshot - NG2's 980 template draws per frame arrive through
   INDIRECT_BUFFERs, which a call-range decode never sees as draws; and the per-range decode still met reserved
   dwords and inline payloads (3,361 registers ever differing, every opcode 00-7F "seen").
3. **Kick mode** (Fable 8a64512, ported): the fork plugin exports `RexNgpuSetKickCallback`, fired at the guest's
   CP_RB_WPTR write on the guest thread; the exe decodes the hardware ring from its own read index to the kicked
   write index, expands INDIRECT_BUFFERs where they execute, applies bin predication as the CP does. Leg ng2_075:
   63,832 kicks, 0 skipped; the front end saw **15.64 M draws to the bridge's 15.72 M** (the template draws
   included); the first compared draws differed only in the draw packet's own `0x21F9-0x21FC`; the type-3 opcode
   set is the real one (22, 27, 2B, 2F, 36, 3B, 3C, 3F, 46, 54, 58, 60-64, plus 21 REG_RMW x1/frame and 45).

Two more traps, then the gate:

- **Ring re-initialisation** (leg ng2_077/078): NG2 re-initialises the ring at every mode change and the plugin
  zeroes both hardware pointers; the front end's read index kept its old value and from then on every kick
  re-decoded the same stretch (2,100 "short ring" stops at one address, the window starting at the tail of an IB
  packet), re-pushing the same snapshots. The plugin now signals the reset through the kick callback (write index
  0xFFFFFFFF, fork ed71ba62) and the front end restarts at 0 (alt 3fba91c); a decode stuck for 16 kicks
  resynchronises at the write index (never needed since).
- **Pairing by arrival order** (leg ng2_079: resets handled, 0 early stops, the front end saw exactly the
  bridge's draws): a per-frame buffer draw matched perfectly while the template draw at 1F037A00 paired with a
  snapshot a frame old - the executions the bridge ran before the front end registered sat at the front of that
  address's FIFO for good. Now both sides count each address's executions since their own last swap and the key
  is (address, ordinal); stale snapshots expire (alt b6347fa).

**Result, leg ng2_080 (13:30-13:34, Chapter 1 gameplay, 11,632 frames): 352,747 draws compared after the
100,000-draw warm-up, 0 registers differ outside the draw packet's own 0x21F9-0x21FC; 0 early stops, 5 ring
resets absorbed, 0 resynchronisations, 0 expired snapshots; the front end saw 10,600,075 draws to the bridge's
10,600,000.** The guest-thread front end reproduces the plugin's register file exactly, on every sampled draw
(every 64th address, all executions), which is the stage-1 gate.

## Stage 2, step 1: where the per-draw registers come from (source census, leg ng2_082)

`NG2_P3SRC=<frame>` records every hooked call's r3-r10 plus 256 bytes behind each pointer-like argument and
every front-end draw's register file; `tools/native_gpu/p3_sources.py` joins each draw to the call whose range
wrote its packet (direct draws) or the IB packet it was reached through (template draws) and votes the source of
each per-draw register's value. Frame 6620: 2,192 draws, 1,503 joined (689 without a containing call - the
per-frame buffers' ring-level IB packets are written by the library's unhooked kick-off path). Result: **the
per-draw registers are device words at the ISSUING call's exit** - `0x2200 RB_DEPTHCONTROL -> +0x2934` and
`0x2203 -> +0x2940` (99.3%, hook 55 = sub_8373CB08, the draw entry), c4-c6 `0x4011-0x4019` in their linear slot
`+0x780 + 4*(reg-0x4000)` (and a second copy at `+0x7C0..`), c201 `0x4325 -> +0x1414`, fetch words `0x4803 ->
+0x048C` and the fetch constants' 5th word `0x481C+6k -> +0x05F8` (72%, hook 51 = sub_8373BC68, the IB issuer,
the rest split with hook 55 by which call the join picked). The earlier "derived" reading came from reading the
device at the wrong call (the innermost containing call rather than the issuing draw entry) and from
cross-frame contamination. Only the draw packet's own words `0x21F9-0x21FC` (initiator, index base, size) and the
resolve registers stay outside the device: those are the draw / resolve call's arguments.

So a stage-2 front end reads, at each draw entry point (hooks 55 and 51 on this route), the device words of the
map for the whole register file, and the call's arguments for the draw packet itself - no packets decoded at all.

## Next: stage 2 (the device object instead of the packets)

The front end still reads the command buffer the game writes; the end state writes none. Stage 2 builds the
register file from the device object and the draw call itself: the device words above cover ~95% of the file
(358 registers equal on every draw, the write-time and draw-time maps agree), and the ~40 per-draw registers need
their sources - the draw entry's arguments and the memory they point at (c4-c6 world matrix, c200, the texture
fetch constants' 5th word, the resolve registers, the draw packet's own words). The front end of stage 1 is the
oracle: a device-built file compared with the decoded one at every draw, on the same thread.

## The front end draws (NG2_P3DRAW=1, leg ng2_087, 14:16-14:19)

Fable's design (a), no queue: on the guest thread, at each DRAW packet the kick-mode front end decodes, the bridge's
`FrontEndDraw` syncs the front end's own register file into the backend (a dirty bitmap of what the front end wrote
since the last draw) and records the draw with the shaders the front end tracked from IM_LOAD / IM_LOAD_IMMEDIATE;
at the XE_SWAP packet `FrontEndSwap` runs the backend's swap and the same hold / letterbox / present logic. The
plugin's draw callback is compare-only; its swap callback only delivers the gamma ramp. One-window presentation is
unchanged (the plugin's IssueSwap copy waits for the backend's swap submission), so no presenter ownership switch.

Result, Chapter 1 route full screen: **14,530,465 draws fed from the guest thread against the 14,530,465 the
plugin saw, 0 failed; 11,682 of 11,700 frames presented (18 held by the reveal); 58-60 fps**; the picture
(title, Chapter 1 gameplay) photographed correct at 3840x1600, ultrawide fill and HUD band intact. The compare
path kept running: 62,932 draws compared, 37 registers differ ONCE each (one draw, frame-boundary shape).

The plugin still parses the ring (for its compare and its guest-memory work); the next steps are P4/P5: stop the
command buffer's consumers one by one - the plugin's parse becomes unnecessary once nothing reads its register file.

**Read-point check (Fable FE_F19, 2026-09-27 14:2x):** Fable fills LOAD_ALU_CONSTANT sources late in the frame,
so its front end must decode at each kick but issue the frame's draws at XE_SWAP (their stage 1b). NG2 does not
need that on the measured population: the stage-1 gate leg ng2_080 (decode at the kick) reported 0 constant
mismatches from memory loads over 352,747 compared draws (~5.1 M LOAD_ALU_CONSTANT packets in the run). Population:
the Chapter 1 route only. If a later chapter shows memory-load mismatches, switch to the 1b shape and use Fable's
FeReread instrument (native-gpu 6244822).

## P5: the plugin stops parsing the ring (NG2_P5EXEC=1, 2026-09-27 evening)

**Side-effect census in shadow (NG2_P5=1, leg ng2_095, frames 6599-6660).** Everything guest-visible the plugin's
command processor does on NG2, per ~62 frames: fence writes (EVENT_WRITE_SHD, literal values) 370 to exactly two
addresses beside the ring (1F03A002 a counter, 1F03A006 a "consumed up to" pointer the game reclaims command-buffer
space by), interrupts 186 (cpu mask 4, three a frame), one REG_RMW a frame (register 0x1841), the read-pointer
write-back to 1F03A03C, the swap, and ~43 waits a frame (register 0x0A31, flags 1F039002 / 1F039006). No MEM_WRITE,
COND_WRITE, REG_TO_MEM, EXT or ZPD. The front end's own record of the same packets: fences EQUAL over 364, interrupts
EQUAL over 183, REG_RMW EQUAL over 61 (the swap and wait "differences" are alignment and register waits).

**Why it had to be one switch, not a gradual hand-over:** the front end cannot write the fences while the plugin
still parses - 1F03A006 tells the game what ring space is consumed, so the game would overwrite commands the plugin
has not read. And interrupts run the game's handler on the thread that dispatches them, so they cannot be raised
inside the game's own kick. Shape: the plugin's command-processor thread stays (an XThread, as the hardware's
interrupt context) but no longer parses; at the end of each kick the front end pushes an ordered batch of records
(fence value / counter, read pointer stamped with the ring epoch, interrupt mask, memory wait, register write outside
the draw ranges - scratch, gamma port, COHER - and the swap) that the thread executes (fork 471b367d; exe side in
ng2_p2_census.cpp, g_p5exec).

**Result, leg ng2_096 (Chapter 1 route, full screen):** the plugin parsed 0 draws; the front end fed 12,662,942
(0 failed); 11,681 of 11,700 frames presented (19 held by the reveal); gameplay windows median 60.0 fps, lowest
56.3; the executor ran 14,467 batches / 5.06 M records (32,315 interrupts, 58,304 fences, 4.72 M register writes),
0 stale read pointers, 0 wait timeouts; title and Chapter 1 gameplay photographed correct. What the plugin still is:
the runtime's graphics system (window, presenter, interrupt thread, vblank, MMIO register file) - the next step
(Fable's P5 "minimal graphics system") replaces that, after which rexgpu-xenos.dll is not needed.

## The game's own graphics system (NG2_NATIVE_GS=1, alt 6f02c22)

The runtime asks the app for its IGraphicsSystem (OnPreSetup may supply one); src/ng2_native_gs.cpp is it. It owns
the D3D12 provider and the runtime presenter (window, swap chain, the F10 / HUD overlays), the GPU register window
(MMIO 7FC80000: reads answered as the plugin answered them, CP_RB_WPTR handed to the front end on the kicking
thread), an executor XThread running the front end's side-effect batches, and the vblank worker. The backend runs on
its provider's device and direct queue and presents into its presenter from the guest thread at each swap (the copy
is submitted before the presenter's fence). rexgpu-xenos.dll's graphics system is never created; the DLL is still
loaded as a plain library so the settings it defines stay registered (vsync, swap_post_effect, the texture pack,
ng2_uw_mode / ng2_fov_k that the presenter reads).

One trap, found by the frame time: the first run held 2.5 fps at exactly 400 ms a frame = four 100 ms memory-wait
timeouts. The flags the GPU waits on (1F039002 / 1F039006) are not written by any packet: the command processor
mirrors every scratch-register write (0x578-0x57F) to memory at SCRATCH_ADDR when that register's bit is set in
SCRATCH_UMSK. The executor now does the same (and completes COHER_STATUS_HOST at once instead of setting the busy bit
the plugin's wait later cleared).

**Result, leg gs2 (Chapter 1 route, full screen, 18:00):** title and gameplay correct; 13,889,918 draws fed, 0 failed;
gameplay windows median 60.0 fps, lowest 58.1; executor 11,400 swaps / 32,773 interrupts / 58,318 fences / 5.04 M
register writes, 0 stale read pointers, 0 wait timeouts; no guest faults.
