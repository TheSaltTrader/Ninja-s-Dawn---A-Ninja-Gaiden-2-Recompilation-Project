# M4 NG2 — first call census of the Direct3D surface

Run 2026-09-16 19:47, NG2 v1.0.20 build + 108 trace hooks, Chapter 7 gameplay
(~900 draws/frame, 60 fps). Raw: `M4_ng2_census1.txt`.

Hooks generated by `tools/native_gpu/gen_trace_hooks.py` from `M3_ng2.json` with
**no change to the generator** — it is game-agnostic as claimed. It reported
"0 state setters + 108 library entry points", degrading cleanly rather than
failing when NG2 has no SetRenderState dispatch table to read.

## Headline

**74 of the 108 hooked entry points fire in gameplay.** The other 34 are init,
teardown or paths this scene does not reach.

**The device is a single object: r3 is `0x40001E80` in every entry point, in every
sample.** Nothing here is ambiguous about which device an offset belongs to.

## What the argument samples say

**NG2 DOES have shadow-state setters, and they are in the matched set.** The
absence of a dispatch table did not mean the setters were missing — it meant there
was no table to name them from. `sub_837369A8`:

    r3=40001E80  r4=00000000  r5=00000000  r6=80000000  r7=00000000  r8=000001F4 ...
    r3=40001E80  r4=00000001  r5=00000000  r6=40000000  r7=00000000  r8=000001F4 ...
    r3=40001E80  r4=00000002  r5=00000000  r6=20000000  r7=00000000  r8=000001F4 ...
    r3=40001E80  r4=00000003  r5=00000000  r6=10000000  r7=00000000  r8=000001F4 ...

r4 is a slot index 0..3; r6 is `0x80000000 >> slot`, a dirty bit; r8 is a constant
**device shadow offset** (0x1F4 here, 0x1E8/0x1E4 for the 55-site pair, 0x1F0,
0x208, 0x170, 0x1C4 elsewhere). That is the shadow-offset information the native
path needs, and it is readable straight off the call arguments without finding the
setters by name. (INFERENCE: that r8 is an offset rather than a coincidence — it is
constant per function across every sample while r4/r6 vary together, which is what
an offset would look like and not what data would.)

**`sub_8373CB08` carries GPU addresses**, 252/frame:

    r3=40001E80 r4=00000006 r7=0000022F r8=161A3003 ... r8=16199003 ... 176CF003

The `...003` low bits and the magnitude are the shape of Xenos fetch constants, so
this is a resource-binding entry point (texture or stream source). INFERENCE, not
yet confirmed against the fetch-constant layout.

**`sub_8373B1F8` passes floats**, 758/frame, the hottest thing in the frame:

    r3=40001E80 r4=00000010 r5=859D3D60 r6=00000019 r8=00000008 r9=3F800000

`0x3F800000` is 1.0f and r5 is a guest pointer, so this is a constant upload —
count and register index in r4/r6. INFERENCE.

## What this does not yet answer, and why

The census is **cumulative per 10 s**, which hides frame structure. Per the Fable
session's hard-won advice, the next tracer revision needs: caller return address
(the call graph, to find where to hook a draw at its exit), per-frame rather than
cumulative counts, the first ring dwords a PM4 emitter writes (so "writes the ring"
becomes "writes a draw packet"), and — the one that cost them weeks — **one frame's
ordered call transcript, verbatim**, because the pass structure of a frame is what
explains where every render target comes from.

The device pointer is already covered: it is constant and logged.
