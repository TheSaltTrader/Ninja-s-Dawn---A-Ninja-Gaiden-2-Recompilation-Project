Reading of the numbers:

- **The device surface is small in both games**: ~80–90 library entry points,
  in the same range as UnleashedRecomp's 42 hooks + 15 stubs. That is the
  per-game HLE.
- **The two games link different XDK builds**: only a few hundred functions
  fingerprint-match, and the library sizes differ (425 vs 234). Address lists
  are per game; the API *shapes* (what each entry point does) should match,
  so naming them once helps twice.
- **Fable II's engine has Direct3D inlined**: its engine calls the library
  only 249 times but 33 engine functions emit PM4 headers themselves, and the
  XDK's inline state setters (which build headers arithmetically, invisible
  to this scan) are surely more. So a function-level HLE alone cannot see
  Fable's state changes. It does not need to: on the 360, `SetRenderState`
  and friends write the **device's shadow register state** and the **draw**
  flushes it. The HLE therefore hooks the library's resource, draw, present,
  clear/resolve/render-target functions (all real calls in both games) and
  reads the shadow state from the guest device struct at each draw. The
  inline emitters that matter (tiling and fences) become no-ops natively.
- **NG2 calls everything**: 675 call sites into 81 entry points; its three
  engine-side emitters are negligible.

Named so far (NG2, by behaviour):

- `sub_8373A918` — device/ring-buffer init (`VdInitializeRingBuffer`, `ME_INIT`)
- `sub_837452C0` — Present (`VdSwap`, `VdGetSystemCommandBuffer`, `VdPersistDisplay`)
- `sub_8373B060` — builds a `DRAW_INDX_2` into an 8 KB allocation (a static command buffer, one caller)
- `sub_8373D570` — the flush/kick (914 insns, `IM_LOAD_IMMEDIATE`, `INVALIDATE_STATE`, `WAIT_REG_MEM`, 43 engine callers)
- `sub_83736568` / `sub_837363D8` — sampler/texture fetch-constant setters (shadow state: `index * 24` bytes, bit inserts; 55 call sites each)
- `sub_8373E9E8` — `D3DResource::Release` (atomic refcount decrement, calls the destroy path; fingerprint-shared with Fable II)
- `sub_8373BD50` — a lock-style entry (176-byte frame, 49 call sites)

Fable II: `sub_82BA2830` init, `sub_82BA34D8` Present, draw variants
`sub_82B9EEE0` / `sub_82B9F038` / `sub_82BA7B28` / `sub_82BA83C0` / `sub_82B99018`
(`DRAW_INDX_2`), `sub_82BA1D40` the most-called library entry (tiling masks,

## What this means for the route

Route A (native backend inside ReXGlue) is viable for **both** games and is the
one to take: hook the ~30 library functions that create/lock/unlock resources,
set shaders and render targets, clear, resolve, draw and present; keep the
CPU recompilation, kernel, audio, input, saves and updater as they are.
Shaders: the guest shader objects (created through hookable library calls)
carry Xenos microcode; the existing translator in the SDK already turns that
into DXBC, so XenosRecomp is optional. The win for Fable II's town is
structural: native textures and buffers uploaded once at creation instead of
the emulation's guest-memory watching, resolves, readbacks and 500–700 MB/s of
re-uploads.
