# v1.1.0 - the native renderer as a test cut (2026-09-27)

The user's direction (2026-09-27 ~01:40): "finish the native pc version and cut a release under the portable
branch so we can test." This is what was built, what was measured, and what is left. Nothing here is published:
the cut went to the user's portable copy only.

## What the cut is

`ng2.exe` v1.1.0 from the alt branch `native-gpu-ng2` (merge of `release/v1.0.25` plus the native work), with
the plugin pair built from NG2's engine fork `native-integration` (`D:\ng2_frameinterp\ng2-rexglue`, which now
carries the five v1.0.25 plugin commits as well). A new settings row, **Native renderer** (on by default, restart
required), drives two startup cvars: `ngpu_backend=true` (the exe brings up the copy of the plugin's D3D12 backend
compiled into it) and `gpu_offload_to_native=true` (the plugin parses PM4 and feeds the backend in lockstep, and
skips its own GPU work). Off = the v1.0.25 plugin path, same pair, same exe.

### One window (the blocker that made the native path unshippable)

Until today the native backend presented from a second raw-D3D12 window while the game's window stayed black:
no F10, no HUD, no letterbox or ultrawide, split focus. Now:

- the backend is brought up on the **plugin's own device and direct queue** (plugin export `RexNgpuGetDevice`,
  captured in the plugin's `SetupContext`), so nothing is shared across devices and every hazard is ordered by
  the one queue the runtime presenter also paints on;
- at each swap, the plugin's `IssueSwap` (which used to return early under offload) asks the exe for the
  backend's gamma-applied guest output (`RexNgpuSetOutputProvider`; the exe waits for the backend's swap
  submission, bounded by `ngpu_present_wait_ms` = 4 ms, and answers 0 during the reveal hold), copies it into
  the runtime presenter's mailbox image, and calls `EndSubmission(true)` inside the refresher exactly as the
  plugin's own swap does;
- the presenter then does what it always did: `ng2_uw_mode` fill / pillarbox (published from the backend's
  copy by `PublishStatCvars`), letterbox, dither, the ImGui overlays (F10, HUD, notices) and the input.

`ngpu_one_window=false` keeps the old separate window for diagnosis. The 5-second log line
`[ngpu] ONE WINDOW: provider calls N (held H, no output 0, waits past 4 ms W); the plugin presented P ...`
is the evidence line.

### Carried from v1.0.25 into the native path

The vendored texture cache (`src/native_gpu_xlat/rtc_d3d12/texture_cache.{h,cpp}`) was re-vendored from the
fork by a three-way merge over the Fable team's native patches (`scratchpad/revendor_tc.py`; one conflict, the
`[gpu prof]` head vs the `[hitch]` wrapper, resolved): async pack builds, the per-frame apply cap, the spare pool
and creation hold, the GPU-ready stage prebuild (its VRAM budget now 30% of the adapter's local budget, 512 MB to
4 GB, on top of `texture_pack_prebuild_mb`), the per-chapter base-texture pre-create. The v1.0.25 ultrawide
detector (pause flags off by default; a solid fade counts as an ultrawide frame) is in the vendored command
processor too, and the Fable team's live cvar mirror (`RefreshInt/Bool/String`) keeps `texture_pack_chapter`,
`texture_pack_path`, `texture_dump`, `texture_dump_path` and `vsync` current in the backend's copies.

Under offload the plugin's own texture cache skips the stage machinery (it draws nothing, so it would write empty
shape and stage lists over the files the backend writes).

## Two defects found by the legs, both fixed

1. **The Chapter 1 card ran at 9 fps on the native path** (plugin path 60). `[ngpu] CPU COST` said 115 ms per
   frame on the plugin GPU thread with 1.3 ms of GPU work; per-phase QPC timers added inside the vendored
   `IssueDraw` (`[ngpu] DRAW PHASES`, on with the GPU profile) totalled under 1 ms, so the backend was innocent.
   Two `cdb -pv` stack samples of the running game (04:35:26 and 04:35:36) both had the GPU thread in
   `ntdll!NtQueryVirtualMemory < KERNELBASE!VirtualQuery < ng2 < rexgpu_xenos!CommandProcessor::ExecutePacketType3`:
   the bridge's `PageReadable()` on shader microcode given by address, two per stage, four per draw, about
   120 us each once the runtime's write watches have split the guest mapping into thousands of regions; the
   card has 240 such draws (gameplay draws carry their microcode inline, so it never showed there). The 09-26
   two-window leg had sat at 110 ms per frame at the same card. Fix: a guarded copy (SEH) into a thread-local
   buffer. Result: the card at 59.8 fps, CPU COST 2.6 ms per frame, and the load phase faster (card at +48 s
   instead of +65 s).
2. **The backend's pipeline cache never loaded the shader storage.** The `Created 439 graphics pipelines from
   the storage` line at startup was the plugin's (04:38:06.376, before the backend came up at .402); the
   vendored `InitializeShaderStorage` was never called, so every launch recompiled every pipeline on demand
   (29-52 ms pipeline waits on the arrival frames where the plugin path has 0) and persisted nothing. Fix: the
   plugin records the runtime's cache root and title id (`RexNgpuGetShaderStorage`) and, under offload, leaves
   the pipeline storage alone; the bridge loads it into the backend right after `Init` (blocking) and closes it
   at `Stop`, so both paths share one `cache/shaders`.

## Known gaps

- The native path's pipeline storage is shared with the plugin path (same format, same code); the first native
  run after this cut still creates the pipelines the plugin path never needed (few) and writes them out at exit.
- The ultrawide fill / pillarbox under offload comes from the backend's `ng2_uw_mode`, published into the
  registry at every swap; the legs ran 16:9 windowed, so the fill itself was not photographed - the presenter
  code path is the plugin path's.
- F10 on the native path (census 08:5x, `tools/f10_census.py` plus the vendored-accessor classification):
  every row reaches its consumer - the backend's startup snapshot (supersampling, accurate depth, fuzzy alpha,
  texture cache, anisotropic: restart-bound as tagged), a live mirror (pack folder / on-off, dump, chapter,
  vsync), the exe's own push (ultrawide FOV factor) or the shared runtime presenter (letterbox, dither, sharpness)
  - except **Antialiasing, which was dead**: nothing in the native tree set the vendored command processor's swap
  post effect, so FXAA was always off under native. Fixed 08:53 (alt e2469c9): the bridge reads
  `swap_post_effect` from the registry when the backend comes up and every 30 swaps and sets the effect on the
  GPU thread. Evidence, ONE WINDOW line: leg ng2_047 (row fxaa_extreme) `backend swap post effect fxaa_extreme
  (output 8bpc false)`; leg ng2_048 (row none) `... none (output 8bpc true)`. The re-cut at 08:57 (exe a4535d7d,
  same pair) is what the portable copy runs.
- `ngpu_backend.dll` (the Fable team's DLL) is not used in one-window mode; the in-exe copy is.

## Re-cut 10:06 - the letterbox follows the reveal hold

## Re-cut 12:26 - the Start and Select menus are 16:9 on both renderers

The user's report on the 10:06 cut, played full screen at 3840x1600: "the ultrawide screen is bleeding on the
edges when pressing start ... the video mist taking the full screen and not be restricted to 16:9", and the same
on Select. What the legs showed (all full screen from here on, the user's rule): the plugin path keeps the menu's
red mist inside the 16:9 band with the world visible at the sides (leg 11:38, `native_renderer=0`); the native
path spreads the mist edge to edge (legs 11:32 and 11:45). Every earlier leg had run a 16:9 window, where the
defect cannot exist, and a parameter-shadowing bug in the leg script had silently run the default route for
every "long"/"none" leg, so no leg had ever photographed a pause menu.

A per-draw dump of one menu frame per path (a file trigger, `dd_now.txt` in the working directory, starts the
existing `[dd]` dump into `dd_dump.txt` on either path) agrees on every field of the two mist draws: vertex shader
1A638253F9911CAD (the UI ortho at c21-c24, compressed like every other 2D quad), pixel shader D58CF95DC03F2A34,
viewport and scissor the whole 2560x1440 target, quads 3839 canvas pixels wide (x -250..3589 and -2308..1531;
three times the 1280 canvas, scrolling), the same 960x360 k_8 texture at 0F70A000 and 256x1 LUT at 0F764000.
The difference sits below the draw setup (what the GPU samples outside the canvas) and is left open; the user
decided "the menu just needs to be forced to 16:9".

The fix (fork + alt, both command processors, `[ng2-menu]`): a depth-off, textured, 4-vertex quad at least
2560 canvas pixels wide is the mist - nothing else in any 2D census is wider than the canvas - and a frame that
draws one is a non-gameplay frame for the scene detector: `ng2_uw_mode` 2, the presenter pillarboxes, no FOV
widening, no 2D compression. Counted at the DRAW (the first build counted inside the vertex-constant upload,
which runs only when the constants change - 7 uploads for ~70 menu quads, so the mist never reached it: leg
ng2_069 `2d=7 mist=0`). Evidence, native leg ng2_070 (12:16-12:17): Start -> `[ng2uw] CHANGE -> mode=2 (3d=480
2d=7 ... mist=2)` and `REVEAL: letterbox -> mode 2` on the same swap, the photograph pillarboxed with the menu in
the band; B -> `mode=1` 0.1 s after the press; Select -> `mode=2 (... mist=2)`, the manual/options screen
pillarboxed. Plugin arm, leg ng2_071 (`native backend off`, 12:22): Start -> `CHANGE -> mode=2 (3d=671 2d=41
... mist=2)`, the same pillarboxed photograph. The menus look the same on both renderers now; the world at the
sides that the plugin path used to show beside the menu is gone with it (the frame is the console's 16:9).
Leg script fixed under a new name (legs_v110b.ps1: the route variable no longer shadows `-Pad`).
Installed 12:26 (alt 4c4111b, fork bec69aff; the P2 exit calls reverted from the generated tree first): exe
388370ab, plugin c9d2d1b6, runtime 22aaa92f; saves backed up to pre_v1.1.0_20260927_122603 on D: and C:.

## Re-cut 14:1x - a fade between the full-width and the 16:9 pictures (user rule 13:5x)

"To prevent any abrupt transitions always use a fade out fade in between ultrawide and 16:9 transition. Example
from death to the continue menu." The switch is decided by the scene detector, so the fade lives there (both
command processors, `[ng2-fade-mode]`, fork 9fda0f59 / alt 399a259): when the detector wants the other mode, the
SHOWN mode - the rendering layout (FOV widen, 2D compression) and the presenter's letterbox together - holds while
a fade level (`ng2_uw_fade`, 0..1000) rises to full black over `ng2_uw_fade_frames` swaps (12 = 200 ms at
60 fps), both switch at full black, then the level falls; a detector that changes its mind during the rise lets
the level fall and nothing switches. The exe's `AspectFadeOverlay` (ImGui, behind the other overlays) paints a
full-window black rectangle from the level on both renderers; under the native path the bridge mirrors the
backend's level into the registry with the other published values. The reveal hold keeps precedence.

Evidence, plugin renderer (leg ng2_085, 14:04:54, the transition into Chapter 1 gameplay): `[ng2uw] fade overlay:
first paint at level 84` at .526, `[ng2uw] fade: 12 swaps to black, switching mode 2 -> 1` at .723 with the
`CHANGE -> mode=1` on the same swap, `fade: back in, mode 1` at .924 - 200 ms out, 200 ms in, the layout and the
letterbox switched together at full black. Native renderer (leg ng2_086, ONE WINDOW, 14:07:58): the same three
lines - overlay first paint at .335, `12 swaps to black, switching mode 2 -> 1` at .844, `back in` at .042 (the
longer rise is the frame rate right after the load, while the stage's pipelines still compile). The route's
menus (Start/Select) take the same path: the detector flips, the fade runs, the switch lands at full black.
Installed 14:11 (alt 035f73a, fork 9fda0f59; P2 exits reverted first): exe ab6d3b7d, plugin ec365224, runtime
8232b2c5; saves backed up to pre_v1.1.0_20260927_140949 on D: and C:. Not published.

## Audit 13:5x - every plugin-side fix is in the native path (user: "verify any fixes we had in the sdk/dll")

`tools/native_gpu/vendoring/audit_vendored.py` pairs each vendored file (`src/native_gpu_xlat/**`) with its fork
counterpart (`ng2-rexglue/src/**`, `include/rex/graphics/**`), normalises the vendoring renames (namespaces, cvar
accessors, include paths, VENDORED / NATIVE PATCH comments) and prints the remaining hunks. 41 pairs, 1,351
differing lines, every hunk read:

- **Identical (0 hunks):** the D3D12 primitive processor and shader, the DXBC translators (alu, om, memexport,
  main), the base shader / translator / disassembler / ucode, the register file and register tables, the shader
  interpreter, every header except the two below.
- **Cvar definitions only** (the description strings survive the filter): texture cache (55 lines), render
  target cache, pipeline cache, deferred command list, draw util, extent estimator, EDRAM cache, flags,
  primitive processor base, fetch translator.
- **Plugin-only mechanics, by design (the NATIVE PATCHes):** in the command processor the `OffloadedToNative()`
  short-circuits, the guest-memory readback data providers, the presenter refresh with the reveal hold (ported to
  the bridge: `[ngpu] REVEAL` lines), the `[hitch]` / `[swap]` texture-pack counters (the bridge prints
  `PACK COUNTERS`), `g_ngpu_device`; in the base command processor the PM4 worker's WAIT_REG_MEM polling, safe-fn
  queue, ring epoch, dirty bitmap, P2 packet recorder, kick callback, `DumpRingState`, the type-0 fast path
  (`WriteRegisterRangeFromRing`) - the vendored base is never driven; in flags.cpp the RenderDoc auto-markers.
- **Native-only optimisations (the Fable kit's):** async submit / cost threads, the upload prologue hoist and
  `TouchRange`, `NgpuParallelCopy`, XXH3 for the skip-unchanged hash, `FastValidChecks`, the texture layout
  cache, the `[draw phases]` timers, the `load && exchange` double check on `texture_became_outdated_`.
- **NG2 feature code - identical in both:** the ultrawide FOV widening, the 2D compression and its exemptions,
  the fades, the scene detector, the Start/Select menu rule, the texture-pack loading paths.

Nothing to port. The runtime DLL (presenter, window, memory) is shared by both paths as the same binary. Re-run
the tool after any plugin-side change; a real fix shows up as a hunk with code in it under a file listed as
identical or cvar-only above.

## How to turn it off

Settings (F10) > Native renderer > off, restart. Or `NG2_NATIVE_GPU=0` in the environment for one launch.
