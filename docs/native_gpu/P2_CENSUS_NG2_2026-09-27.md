# P2 attribution census - NG2 results (2026-09-27)

Full-native plan phase P2 (FULL_NATIVE_PLAN.md, Fable's native-gpu 5627323; the method and format are in
P2_CENSUS_FORMAT.md). Every PM4 packet the plugin executes, attributed to the guest Direct3D entry point (or the
mechanism) that produced it; "unattributed" is the number to drive to zero before a native front end can claim
to replace the command buffer.

Reports and JSON: `docs/native_gpu/p2/p2_census{4,5_menu,6_cine}_report.txt` / `.json`. The recordings (`*.bin`,
~40 MB per census) stay beside them, out of git.

Two things the census settled about NG2 that the plan's Fable numbers do not carry over:

- **NG2 does not tile.** Every draw in every censused frame ran with bin select 0xFFFFFFFF. Fable's Fairfax
  issues its scene three times through predicated tiling; NG2's ~1,730 draws per frame are each issued once, so
  the P3/P4 "draw once" lever that is Fable's biggest single win does not exist on NG2, and NG2's per-draw cost
  is already inside the frame (6.7-8.8 ms of GPU-thread CPU per frame in gameplay, log ng2_046).
- **Most NG2 draws are template replays.** 980 of ~1,730 gameplay draws per frame (57,048 of 93,249 in the
  cinematic) are executed from one 24-packet `DRAW_INDX_2` block (auto-index draws, one dword each) that the
  library wrote once at device creation into its system command buffer at physical 1F037980; the engine calls it
  through `sub_8373BC68` with an INDIRECT_BUFFER packet whose count selects how many of the 24 to run, after
  writing the state for that batch. A native front end sees "draw K times with the current state" at that call.

## How each packet found its producer

1. **Same-frame call range** (the device's ring write cursor at device+0x30, read at the entry and every exit
   of the 108 hooked entry points; the exit is injected before every `return;` of the recompiled body): the
   per-frame command buffers.
2. **Last writer per 64-byte block, since the first library call**: buffers recorded earlier and replayed. The
   device pointer is learned at the first library entry whose +0x30/+0x38 look like cursor/limit; learning it at
   the first swap missed everything the library writes at device creation.
3. **Via INDIRECT_BUFFER**: packets executed from a buffer no hooked call wrote are credited to the call that
   issued the IB packet (the plugin records each IB's target range as a marker).
4. **Engine inline** after or before a hooked call (within 256 bytes of a range end or start): 32 `DRAW_INDX`
   per gameplay frame written by engine code 56 bytes after the state flush `sub_8373BD50` returns, and the
   register set-up blocks callers write ahead of a draw call.
5. **The primary ring** (`--ring BASE:SIZE` from the plugin's InitializeRingBuffer line): the library's kick-off
   writes the ring through the ring's own pointer; six INDIRECT_BUFFER calls per frame.

Rule 4 is the one that names direct writers. On NG2's Chapter 1 there is exactly one such draw path (the 32
`DRAW_INDX` after `sub_8373BD50`); everything else is the library.

## P3 inputs from NG2's device object

The XDK device layout NG2's library reads matches the one Fable documented (M4_fable2.md): the write cursor at
+0x30 with its limit at +0x38 (`sub_83734370` begins `lwz r11,48(r31); lwz r10,56(r31); cmplw`), the dirty masks
at +0x00..+0x28 (all-ones in the discover dump; `sub_8373BD50` ORs +16/+24), the vertex constants at +0x780
(`sub_8373BD50` flushes `device+1920` with 16,384 bytes) and the pixel constants at +0x1780 (`device+6016`,
17,408 bytes), state at +0x2E30/+0x30E8, and the shader slot region at +0x3190 (`device+12688`). Fable's
+0x3484 second cursor is zero on NG2 (the +0x3400 area is all zeros). The device object is at 40001E80 in this
build. So a device-object front end (P3) reads the same fields on both games; the register block at
+0x2880..+0x2934 and the fetch constants at +0x480 are to be confirmed on NG2 against the plugin's register file
at a draw, which is P3's first step.

## What is not covered yet

- Only the scenes the scripted route reaches: title, Chapter 1 cinematic and gameplay. Later chapters need a
  save loaded (the live pad-file channel reaches the load-game menu; see the project notes), and the census
  should be repeated there and on a full-screen video and the results screens before P4 is called complete.
- Metric 2 is n/a until a front end exists.
- The hooked set is the 108 entry points of `native_gpu_trace.toml`; the census reads 0 with them, so nothing
  outside that set wrote a packet in these scenes - but a scene that uses a library function outside the set
  would show up as unattributed, which is the point of running more scenes.
